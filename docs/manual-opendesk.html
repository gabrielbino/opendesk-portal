Guia de domínio

Dominar o OpenDesk, do clique ao banco

Um portal full-stack com 57 páginas, 22 routers, 108 tabelas e integrações reais. Este manual mostra como as peças se ligam, o que editar em cada arquivo, e ensina banco de dados e Docker partindo do zero.

01 Visão geral

OpenDesk é um monólito modular: um único servidor Node/Express serve tanto a API quanto o front React já buildado. Não há microserviços — há módulos (Suporte, Projetos, Almoxarifado, Gestão de Negócios, Indicadores, Administração) que compartilham a mesma base de código, o mesmo banco e a mesma camada de permissões.

Ao redor do portal existem serviços e agentes de apoio. Este é o mapa mental que você deve carregar antes de abrir qualquer arquivo:

frontend

React 19 + Vite

SPA em client/. Roteamento com Wouter, dados via tRPC + TanStack Query.

backend

Express + tRPC

API tipada em server/. Um router por módulo, tudo montado em /api/trpc.

dados

MySQL + Drizzle

Schema em drizzle/schema.ts; queries em server/db.ts e server/db/*.

02 Como tudo se conecta

A pergunta mais importante para dominar o projeto: o que acontece quando você clica em algo na tela? Siga o caminho — cada seta é um arquivo que você pode abrir.

Os pontos de entrada (abra estes primeiro)

ArquivoO que faz
client/src/main.tsxRaiz do front. Cria o cliente tRPC (aponta pra /api/trpc, usa superjson, manda cookie) e envolve o <App/> nos providers.
client/src/App.tsxTodas as rotas (Wouter). Cada rota é embrulhada por ProtectedRoute (exige login) e PermissionGuard (exige permissão do módulo).
client/src/lib/trpc.tsO objeto trpc tipado que as páginas importam para chamar o backend.
server/_core/index.tsSobe o Express: body parser, storage, OAuth, monta o tRPC em /api/trpc, serve o React (Vite em dev, estático em prod) e registra as "pontes" dos agentes + rotas agendadas.
server/routers.tsO appRouter: junta os ~25 routers de módulo num só. É o índice do backend.
server/_core/trpc.tsDefine publicProcedure, protectedProcedure e o router(). Aqui mora a checagem "tem sessão?".
server/_core/context.tsLê o cookie de sessão (JWT) em cada request e monta ctx.user — a identidade que os routers usam.

03 Mapa do projeto

A regra de ouro: quase todo módulo aparece em 3 lugares — uma página em client/src/pages, um router em server/routers, e (se persiste dados) tabelas em drizzle/schema.ts. Aprenda a pular entre esses três e você anda por qualquer feature.

Técnica de leitura

Escolha UMA feature simples (ex.: a lista de chamados). Abra a página, ache o trpc.suporte…useQuery(...), pule pro router correspondente em server/routers, veja qual função de server/db.ts ele chama, e qual tabela do schema.ts ela toca. Fez isso 3 vezes e o padrão inteiro "clica".

04 Sistemas transversais

Quatro mecanismos aparecem em todo módulo. Entendê-los é entender 80% do projeto.

1 · Autenticação & sessão

Login em server/routers.ts (auth.login) confere a senha com bcrypt e grava um cookie de sessão assinado (JWT via jose). A cada request, server/_core/context.ts lê esse cookie e coloca o usuário em ctx.user. No front, client/src/_core/hooks/useAuth.ts sabe quem está logado.

2 · Permissões (o coração)

shared/permissions.ts tem uma árvore única (PERMISSION_TREE) — dela saem: a tela de atribuir permissões, a visibilidade dos cards no hub, e as checagens no servidor. admin pula todas as checagens.

CamadaArquivoPapel
Definiçãoshared/permissions.tsMODULES, ACTIONS, PERMISSION_TREE
Front (esconde)components/PermissionGuard.tsxNão renderiza a página se faltar permissão
Server (bloqueia)server/permissionMiddleware.tsrequirePermission(MODULES.X, ACTIONS.Y) no router

3 · Camada de integração (dados de "ERP")

Três camadas, nunca copie a chamada de query em vários módulos:

  • server/erpApi.ts — transporte: login, token, executarQuery(chave, params).
  • server/erpQueries.ts — uma função por query nomeada, já normalizando as colunas.
  • o módulo — só mapeia pro seu domínio e persiste.

4 · Acesso ao banco

server/db.ts (e server/db/*.ts por módulo) concentram as queries Drizzle. Ninguém escreve SQL cru espalhado — passa por aqui. A conexão fixa timezone=Z (UTC); a exibição em horário local fica na apresentação.

05 Trilha de estudo

Ordem sugerida para sair do zero ao domínio, sem se perder nos 600 arquivos.

  1. Rode o projeto (seção Docker abaixo) e navegue como admin. Ver funcionando primeiro dá contexto pra tudo.
  2. Leia o fluxo (seção 02): abra main.tsx, App.tsx, server/_core/index.ts e server/routers.ts. Não precisa entender tudo — só o formato.
  3. Siga UMA feature ponta a ponta: página → hook tRPC → router → db.ts → tabela. Recomendo Rupturas (tem os 3 lados claros).
  4. Estude shared/permissions.ts: entenda a PERMISSION_TREE e como um módulo "aparece". É o esqueleto do sistema.
  5. Abra o banco (seção 06) e cruze o que viu no código com as tabelas reais (SHOW TABLES, SELECT).
  6. Faça uma mudança pequena guiada pelo Cookbook (seção 08): mude um texto, adicione uma coluna, crie um endpoint. Aprender editando fixa.
  7. Explore os componentes reutilizáveis (PanelHeader, KpiCard, DataTablePagination): são os "tijolos" de toda tela nova.

06 Banco de dados (do zero)

O que é: o MySQL é um servidor que guarda os dados em tabelas (como planilhas): cada tabela tem colunas (campos) e linhas (registros). Você conversa com ele em SQL. O portal tem dois bancos no mesmo servidor:

portal

opendesk

Os dados do portal: usuários, chamados, projetos, inventário, configs. 108 tabelas.

ERP fake

demo_erp

Um "ERP de cliente" sintético que a query-api consulta para os painéis (vendas, estoque, pedidos).

Jeito 1 — visual (recomendado para começar)

Instale um cliente gráfico gratuito — DBeaver (ou TablePlus / MySQL Workbench) — e conecte com estes dados. Você vê as tabelas numa árvore, clica e navega as linhas como numa planilha.

Jeito 2 — linha de comando (dentro do container)

Sem instalar nada: entre no MySQL que já roda no Docker. O -it abre um terminal interativo; o charset garante acentos certos.

bash
# abrir o cliente MySQL dentro do container, já no banco opendesk
docker exec -it opendesk-dev-mysql mysql --default-character-set=utf8mb4 -uroot -pdev opendesk

SQL essencial (navegar, adicionar, editar)

sql
-- que tabelas existem?
SHOW TABLES;
-- quais colunas tem uma tabela?
DESCRIBE sys_usuarios;
-- LER: ver 10 usuários (só algumas colunas)
SELECT id, name, email, role FROM sys_usuarios LIMIT 10;
-- FILTRAR + ORDENAR
SELECT * FROM suporte_chamados WHERE status = 'Novos' ORDER BY createdAt DESC;
-- ADICIONAR uma linha
INSERT INTO sys_departamentos (name) VALUES ('Marketing');
-- EDITAR
UPDATE sys_usuarios SET role = 'admin' WHERE email = 'admin@opendesk.local';
-- APAGAR (cuidado: sempre com WHERE!)
DELETE FROM sys_departamentos WHERE name = 'Marketing';
-- CRUZAR tabelas (JOIN): chamados com o nome do departamento
SELECT c.title, d.name AS depto
FROM suporte_chamados c
LEFT JOIN sys_departamentos d ON d.id = c.departmentId
LIMIT 20;
Tabelas para conhecer

sys_usuarios, sys_departamentos, sys_grupos_permissao (base); suporte_chamados (Suporte); projetos_base (Projetos); ti_inventario_itens (Almoxarifado); superestocados_*, rupturas_*, validades_curtas_itens (Estoque); monarq_* (Monitor de Integrações). Os prefixos indicam o submódulo.

Como o schema é definido e alterado

A forma das tabelas vive em drizzle/schema.ts (fonte da verdade). Não se usa drizzle-kit generate/migrate aqui (está dessincronizado). Para mudar o schema, roda-se SQL idempotente à mão (ex.: ALTER TABLE … ADD COLUMN …) e atualiza-se o schema.ts + o dump scripts/bootstrap/schema.sql. Veja o Cookbook.

07 Docker (do zero)

Docker empacota programas com tudo que precisam, para rodarem igual em qualquer máquina. Três palavras:

Imagem

O "molde" — um pacote pronto (ex.: mysql:8). Você baixa/builda uma vez.

Container

Uma imagem rodando. Descartável: pode parar/apagar e criar de novo.

Volume

Onde os dados persistem mesmo se o container morre (é onde o MySQL guarda o banco).

O arquivo docker-compose.yml descreve todos os serviços do OpenDesk de uma vez. Ele sobe: db (MySQL), query-api, portal e um sync-init que popula os painéis.

Comandos que você vai usar toda hora

bash — na raiz do projeto
docker compose up -d        # sobe tudo em segundo plano
docker compose ps           # o que está rodando
docker compose logs -f portal   # acompanha os logs de um serviço
docker compose down         # para tudo (MANTÉM os dados)
docker compose down -v      # para E APAGA os dados (re-bootstrap no próximo up)
docker compose up -d --build portal   # rebuilda só o portal após mexer no código

Espiar / navegar os dados dentro do container

bash
# um terminal shell dentro do container do banco
docker exec -it opendesk-dev-mysql bash
# ou direto no MySQL (como na seção 06)
docker exec -it opendesk-dev-mysql mysql -uroot -pdev opendesk
# ver containers e volumes do sistema
docker ps
docker volume ls
Windows — PATH do Docker

Se o terminal disser docker: command not found, o Docker Desktop precisa estar aberto (baleia verde) e, no Git Bash, adicione ao PATH: export PATH="$PATH:/c/Program Files/Docker/Docker/resources/bin".

Como o bootstrap funciona

Na primeira vez que o db sobe com o volume vazio, o MySQL roda sozinho os scripts em scripts/bootstrap/ e services/demo-erp/ (schema + admin + dados de demo). Depois disso ele não roda de novo — por isso down -v (que apaga o volume) é o jeito de "começar do zero".

08 Cookbook: como faço para…

…rodar em modo de desenvolvimento (com hot reload)

bash
docker compose up -d db     # só o banco no Docker
pnpm install                # uma vez
pnpm dev                    # portal em http://localhost:3000 (edita e recarrega)

…mudar um texto/label na tela

Procure o texto direto em client/src (ex.: no VS Code, Ctrl+Shift+F). Edite o .tsx, salve — com pnpm dev a tela recarrega sozinha.

…adicionar uma coluna numa tabela

  1. Rode o ALTER TABLE no banco (seção 06). Ex.: ALTER TABLE sys_usuarios ADD COLUMN telefone VARCHAR(20) NULL;
  2. Reflita a coluna em drizzle/schema.ts (na definição da tabela) para o TypeScript enxergar.
  3. Atualize o dump: regenere scripts/bootstrap/schema.sql (assim quem clonar já nasce com a coluna).

…criar um endpoint de backend (tRPC)

  1. No router do módulo (server/routers/x.ts), adicione uma query/mutation, protegida com requirePermission(MODULES.X, ACTIONS.Y).
  2. Chame do front com trpc.x.novoEndpoint.useQuery(...) — o tipo aparece sozinho.

…adicionar uma página/módulo novo

Siga o checklist de permissão do CLAUDE.md (7 passos): chave em MODULES → nó na PERMISSION_TREE → rótulo no permissionMiddleware → rota no App.tsx com PermissionGuard → card no hub → router com requirePermission.

…recomeçar o banco do zero

bash
docker compose down -v && docker compose up -d   # apaga e re-bootstrapa

…debugar

Front: Console e aba Network do navegador (veja a chamada a /api/trpc). Back: os console.log aparecem no terminal do pnpm dev (ou docker compose logs -f portal). Antes de fechar: pnpm check (tipos) e pnpm test.

09 Glossário

TermoÉ…
tRPCJeito de chamar o backend com tipos compartilhados — a função no server vira uma função tipada no client, sem escrever URLs/JSON à mão.
ORM / DrizzleCamada que deixa você consultar o banco escrevendo TypeScript em vez de SQL cru. Drizzle é o ORM usado aqui.
superjsonFormato que preserva tipos ricos (datas, etc.) entre client e server.
Vite / HMRFerramenta de build do front. HMR = a tela atualiza sozinha ao salvar, sem recarregar tudo.
JWT / cookie de sessãoUm "crachá" assinado guardado no cookie que prova quem você é a cada request.
SPASingle Page Application — o React troca de tela sem recarregar a página inteira.
Imagem / Container / VolumeMolde / molde rodando / lugar onde os dados persistem (ver seção 07).
bind mount"Espelhar" uma pasta do seu PC dentro do container (é como os scripts de bootstrap entram no MySQL).
idempotentePode rodar várias vezes sem estragar — rodar de novo dá o mesmo resultado (ex.: INSERT IGNORE).
